# 公演全体の定員管理

## 仕様

- ADMINの「受付可能な総枚数」は公演ごとの総上限。1〜1,000,000の整数。空欄（DBのNULL）は総数制限なし。
- 従来の1申込上限（1〜20枚）は別に維持する。
- 未確定 pending と確定 confirmed の枚数を合算。キャンセル cancelled と削除済み deleted_atありは除外する。
- 残数＝総定員−有効予約枚数。残数0は「予約受付終了（定員に達しました）」と表示して入力・送信を無効化する。
- 手動停止・期間外の判定を優先する。定員到達によってenabledは変更しないため、キャンセル後に残数が回復すれば、受付期間内・有効状態で自動再開する。
- 定員未設定の場合も予約済み枚数は表示し、残数は「制限なし」と表示する。
- 予約済み枚数を下回る定員への変更は拒否する。
- キャンセル復活、予約枚数の増加も定員チェックの対象。既存予約を除いた占有枚数＋更新後の枚数で判定する。

## 排他制御

申し込み・予約編集・キャンセル・削除・定員変更の各トランザクションは、先に公演行をSELECT FOR UPDATEでロックする。
ロック取得後の有効予約合計で判定し、更新をコミットするまでロックを保持する。
管理者操作も同じロック順（公演→予約）とし、同時申込と枚数増加が競合しても上限を超えない。
アプリ外から直接予約テーブルへ書き込む運用は対象外。必ずサービス層を経由する。
クライアントの残数は最大30秒ごとの再取得で更新される。古い表示で送信されてもサーバーが最新残数で拒否する。

## DB

既存DBには db/migrations/001-event-capacity.sql を一度だけ適用する。
追加はticket_events.capacity（NULL可）・範囲CHECK・有効予約の集計用部分インデックスだけ。
既存予約は変更しない。既存公演のcapacityはNULLで従来動作を維持する。
新規構築用db/tickets.sqlにも同じ構造を反映済み。新規スキーマ作成後に001を重ねて適用しない。
今回の適用先は照合済みNeon開発ブランチのみ。本番は未適用。

## 検証

- npm run test:tickets：既存回帰と定員管理テスト（ローカルPostgreSQL互換エミュレーター）。
- node --import tsx scripts/ticket-capacity-db-test.mts --development-db：照合済み開発ホストのみで実DBテスト。
  既存予約3件が前提。専用の架空公演・予約で同時実行、キャンセル、編集、無制限を検証する。
  SMTP処理は呼ばず、新規メールジョブがpendingで作成され、編集・削除で無効化されたものを含め送信試行0件であることを確認する。
  最後に自分で作成した専用データだけ片付け、既存予約・既存公演設定が完全一致することを確認する。
  実DBテストはDBへの書き込みがあるため、本番や不明なホストでは実行しない。
